# 卡牌连接整体落地计划

保存与审阅日期：2026-10-23（北京时间）；实施更新：2026-10-24。状态：**第一版本机可游玩，已完成全量回归**。本文保留原设计目标；实际数据覆盖、实现差异与验证以 [第一版实现记录](card-link-implementation.md) 为准，不能把全部设计条目视为已完成。

实施前先读 [项目接手手册](PROJECT_HANDOFF.md) 和根目录 [AGENTS.md](../AGENTS.md)，重新核对届时的代码、数据和运行状态。以下数量是 2026-10-23 的只读观察，不作为未来迁移基线。

## 1 产品目标和已确定的选择

在娱乐模式中新增“卡牌连接”：通过真实的同期队友关系，将两名 CS 职业选手连接起来，结合选手知识、路线规划和抽牌策略。

首发同时提供两种玩法，各自支持练习、每日挑战、2—8 人好友房和 1v1 天梯。内部按阶段实现，不能把先完成单人误写成用户接受缩减首发范围。

| 玩法 | 核心体验 |
| --- | --- |
| 无限手牌 | 自由搜索选手并构造连接链，寻找更短路线 |
| 限定手牌 | 独立随机起手，出牌自动补牌，利用换牌和刷新优化路线 |

两种玩法独立匹配、独立天梯积分和排行榜。多人使用同题独立竞速，不采用公共链轮流接龙；先比较路径长度，再比较用时。限定手牌保留独立随机带来的手气差异，不宣称双方完全对称。

参考 [cslink.cc](https://cslink.cc/cslink/) 的选手卡牌、搜索、拖放连接、关系说明与模式组织。2026-10-23 查看了公开首页、关于说明和练习界面；没有完整验证参考站多人内部规则。其关于说明使用 HLTV 比赛与阵容证据，本项目采用用户选择的“同期在役队友”，不将任期重叠描述成共同参加过某场比赛。

历史范围为 CS:GO 和 CS2。娱乐模式总入口继续保留单色勾线小鸭；新玩法用两张叠放卡牌的单色镂空 SVG，匹配现有 Lucide 图标，不依赖各系统表现不同的彩色 emoji。

### 1.1 用户确认的限定手牌规则

- 用户补充的“无限模式每打出一张……”已澄清为作用于**限定手牌模式**。
- 起手必有一条可解路线；同题同候选牌池，不同玩家独立随机起手和补牌。
- 有效出牌自动补牌；有效出牌或撤下弃牌各获得一次共享机会，最多持有两次；单张换牌或整手刷新每次消耗一次（2026-10-24 用户调整）。
- 无解判定允许重新排列桌面牌，不只检查当前接法。
- 每次确认为无解都可自动保底一次，不扣手动机会；不能连续盲目随机直到碰巧可解。
- 已打出的牌撤下即弃牌，本题不能再使用。

### 1.2 本方案采用的默认参数

起手 7 张、初始手动机会 0 次；每日和天梯每题 180 秒；好友房和天梯默认 3 题；Elo 初始 1000、K=32。这些是上轮计划采用的默认值，不是参考站已核实参数。集中保存为带版本的规则配置，后续调参只影响新局。

## 2 游戏规则和状态边界

### 2.1 公共规则

- 起点和终点固定，中间放选手卡。相邻两人为有效队友时该连接成立，全链成立才记录有效成绩。
- 同一条链不能重复出现同一真实选手，别名及大小写重复不能绕过限制。
- 各连接可发生在不同年代，不要求整条链在同一时间成立。
- 跳数是边数：A → B → C 为 2 跳、1 张中间牌。
- 服务端保存本题最好有效路线；之后尝试更差或无效路线不覆盖最佳成绩。
- 服务端拥有计时、判定、发牌、机会、锁定和结算权。前端只展示及提交意图。
- 多人过程中只公开对手是否连通、是否锁定，不公开其路径、手牌、牌堆或证据；结束后统一揭晓。

难度默认按已发布关系图的最短距离划分：简单 2 跳、普通 3 跳、困难 4—5 跳。端点优先采用对应难度中的熟悉选手。无限玩法允许使用本局图内的有效选手；限定玩法只能使用本题候选牌池及本人实际获得的牌。

### 2.2 无限手牌

搜索昵称及已审核别名，支持拖入、点击插入、排序、移除。每次正式放置后反馈相邻关系，全链连通则更新最佳成绩，仍可继续优化。练习不限时，可放弃查看示例最短路径；每日和多人过程中不直接揭示答案。

### 2.3 限定手牌

| 项目 | 规则 |
| --- | --- |
| 起手 | 7 张；独立随机，但每人的起手均存在至少一条完整路线 |
| 有效出牌 | 插入后至少与一侧相邻卡构成有效连接；完全不相连则退回，状态和资源不变 |
| 补牌 | 成功出牌后补至 7 张，余牌不足则补入剩余牌 |
| 机会 | 有效出牌或撤下弃牌各获得 1 次，上限 2；初始 0 次；单张换牌或整手刷新每次消耗 1 次 |
| 手动操作 | 换 1 张，或整手刷新；共享一次机会，用后归零 |
| 重排 | 桌面卡可移动，但不能额外补牌或奖励机会 |
| 弃牌 | 撤下的桌面牌、换掉或刷新的旧手牌进入本题弃牌区，不能再抽到 |
| 自动保底 | 手动操作或出牌完成后，当前可用牌无解则整手刷新，不扣手动机会 |
| 自动保底范围 | 使用手牌、桌面牌及固定端点判断，允许重排；不把未来牌堆算作当前可用牌 |

每张真实选手牌在一题中只有一份，卡牌必须恰好归属于未抽、手牌、桌面、弃牌之一。固定端点不在牌堆中。复制卡牌、重复请求、重排或重新连接不能产生第二次奖励。

#### 无解刷新和耗尽

自动刷新先排除本次将被弃置的旧手牌，再在桌面牌和剩余未抽牌中寻找恢复方案。只有证明新增不超过 7 张手牌即可形成完整路线，才直接构造包含该路线所需牌的新手牌，其余槽位随机补足。它不是随机重抽的循环。

当弃掉了所有路线的必经人物，或当前剩余牌无法在一次整手补充内恢复完整路线时，进入“剩余牌池无可恢复路线”，结束本题并保留已有最佳成绩。不复活弃牌、不无限刷新。正常牌池耗尽与数据库/缓存故障必须使用不同错误和处理路径；系统失败不能算玩家输题。

刷新、弃牌、补牌、机会变化、最佳成绩和自动保底的结果属于同一个原子操作；不得先扣机会，再因计算或存储失败留下半个状态。

### 2.4 赛制和成绩

| 场景 | 默认规则 |
| --- | --- |
| 练习 | 不限时、不影响天梯，可放弃查看答案 |
| 每日 | 每玩法每天一道，北京时间 00:00 更新；可反复重做，不限答题时间，次日零点截止；每账号/日期/玩法只取最佳成绩上榜 |
| 好友房 | 2—8 人，默认 3 题、每题 180 秒；房主可选 120、180、300 秒 |
| 天梯 | 1v1、3 题、每题 180 秒；无限与限定分别匹配 |

单题：连通优先，再比跳数少，再比首次达到该最佳跳数的服务端用时；相同则并列。整场：完成题数多优先，再比已完成题总跳数、总用时；仍相同则平局。每日按单题规则排名，限定每日明确标注独立发牌。

首位连通不提前结束。主动锁定后不能修改；全员锁定或截止后结算。天梯以整场结果计算独立 Elo，好友房、每日和练习不影响 Elo。

每日题目和关系图按日期、玩法固定；刷新页面继续原局。完成或退出后可以重做，重做重新发手牌，尚未结束则恢复同一局。排行榜在所有已结算连通成绩中选每个账号当天该玩法的最佳完整成绩：跳数优先，跳数相同用时短优先；不把不同局的最少跳数与最短用时拼接。旧重做成绩也参与比较，失败或较差成绩不覆盖最佳；游客认领后与账号记录合并去重。每局随机状态独立持久化，重复请求不重新发牌。天梯可重连但截止时间继续；主动退赛按整场认负处理，避免用弃权抹掉失败。好友房退赛保留已有回合成绩，后续未完成，不参与胜者判定。

## 3 任期数据和关系库

### 3.1 兼容新增，保留旧契约

2026-10-23 只读核查：669 条选手记录，647 条启用；存在 15 组昵称仅大小写不同的候选重复。旧 `team_history` 是去重后的队名字符串数组，无法恢复日期和多次回归。

保留原字段、原选手 ID 和猜选手/海龟汤行为，新增结构化生涯资料，不直接将旧字段改成对象数组。

| 实体 | 职责 |
| --- | --- |
| 选手身份映射 | 既有 playerId、真实人物 ID、别名和来源页面标识 |
| 战队分队身份 | 稳定分队 ID、组织归属、名称及已审核别名，不混合主队/学院/国家分队 |
| 任期及证据 | 人物、分队、游戏范围、起止日期、精度、角色、状态、原始文字及来源 |
| 任期修订与审核 | 输入来源、基准版本、差异、冲突、审批和人工锁定修正 |
| 已发布关系版本 | 不可变节点、边、重叠区间与证据引用、数据版本及构建规则版本 |

同队多次回归保存多段，当前队伍也要保存。确认重复人物后只在新关系库中映射为同一节点，不删除原记录、不自动按昵称小写合并。

### 3.2 建边规则

两名不同人物在同一分队有确定重叠的在役选手任期，才建立边。

- 使用日级日期区间，内部开始包含、结束不包含；同一天交接不自动视为重叠。
- 正式在役与已确认的租借计入，租借按实际效力分队归属；明确下放、非活跃及员工角色不计入。
- 临时替补和试训保留资料，有明确在役证据且经审核后才建边。
- 月、年或未知日期保留精度，不补假日期；只有可确定的重叠才自动建立关系。
- Present 截止于该数据版本的采集边界，不无限推至未来；冲突任期进入审核。
- 同队 CS:GO 到 CS2 的持续效力不因页面分区切换而虚构离队；两个游戏分区的重复描述也不能生成重复边。
- 相似队名不等于同一分队；更名由来源身份与审核映射确认。

边详情展示队伍、重叠日期、来源。缺少边时提示“当前关系库未收录有效连接”，不能把数据缺失说成历史上绝对不是队友。

### 3.3 抓取和审核

扩展现有 TH 解析器已经提取的日期、队伍与角色，不另写一套重复解析。现有字符串历史输出继续保留，新任期输出包含原始条目和日期精度。

流程：动态基准导出 → 抓取 → 结构化任期 → 差异预览 → 审核 → 候选关系图构建 → 校验 → 发布。

全量处理 669 条记录并输出覆盖报告，分别统计成功、无历史、身份不明、日期不明和抓取失败。网络失败不清空旧资料，人工修正不被自动覆盖，旧客户端省略新字段不能清空任期。

复用已有 Bearer 权限、expected 冲突检查、提交幂等和审核入口。任期是独立版本化资源，不把复杂任期对象硬塞进旧 `normalizeTeamHistory`。后台同一选手页面显示任期时间轴、来源、冲突、关系增减预览。

抓取使用已有请求间隔和恢复机制；首轮全量，后续按来源修订/内容哈希跳过无变化的解析与提交，保留周期性完整核对能力。不因“并行优化”提高到不受控抓取并发，也不在游戏请求里访问外站。

## 4 性能审阅与修订

### 4.1 审阅结论

| 原方案风险或不足 | 本次修改 |
| --- | --- |
| “建图、算路径”没有说明执行时机，容易每次出牌查任期并重建 | 构建在独立后台任务/命令中执行，游戏热路径只读已发布邻接表 |
| “允许重排后无解”容易被实现成枚举所有排列 | 可用节点诱导子图 BFS；恢复手牌用带节点成本的最短路 |
| 随机保证有解容易写成无界重试 | 先取得可行路线，再填充和打乱手牌；候选搜索有明确预算和失败结果 |
| Redis、SQL、操作日志职责模糊，容易形成多个权威状态 | SQL 是持久状态与操作回执的权威；Redis 负责匹配、通知和可重建调度/缓存 |
| 多人每次私有出牌可能重写和广播整个房间 | 每人独立修订和私有增量；公共状态仅在公共信息变化时广播 |
| 游戏、个人结果重复保存关系图和卡牌资料 | 按不可变版本引用，共享每场结果；历史通过显式 codec 读取 |
| 两玩法乘四场景容易复制八套业务流程 | 一个规则核心、两个明确策略，场景负责时限、权限和结算 |
| 直接复制图寻领域实现容易引入隐藏耦合 | 复用公共工具，借鉴可靠性模式，领域 store/view/codec 不跨游戏复用 |
| 只说“性能应足够”，缺少可核查依据 | 补充复杂度、请求工作量和隔离性能验收目标 |

本轮是代码与设计审阅，没有执行新玩法基准，以下数字均是实施验收目标，不是已测结果。

### 4.2 关系图构建与缓存

1. 按稳定分队 ID、游戏范围分组，任期排序后扫描活跃区间，避免全体任期无条件两两交叉。复杂度以排序及实际候选重叠数计；极端密集分组仍可能产生平方数量关系，要记录候选数和耗时。
2. 同一人物对的多段重叠合并为一条邻接关系，证据段另存；邻接检查使用 Set 或等价索引，不能线性扫描全部边。
3. 构建任务读取固定任期修订的一致快照，发布前核对源修订；源已变化则候选过期，不覆盖更新版本。多个审批合并触发一次构建，避免逐字段批准就全量重建。
4. 首版采用完整、确定性构建，按内容哈希去重相同产物；不同时维护难以验证的增量图修补链。
5. 出题时使用预先计算的连通分量、按难度筛选的端点候选；后台可逐源 BFS 生成候选，不预存所有可能路径。完整路径数量可能指数增长，禁止枚举。
6. 每进程按 graphVersion 缓存不可变邻接表，同一版本并发加载合并为一个 Promise；历史版本用有界 LRU，活跃局加载有保护。内存淘汰只影响缓存，不能删除持久历史。
7. 数据库中的已发布版本指针是事实来源；Redis 通知只作加速，通知丢失也能在新局创建时读到最新版本。正在进行的局始终按自己的版本读图。

### 4.3 无解判定与发牌算法

当前可用节点为端点、桌面和手牌。允许任意重排、没有必须经过某张牌的约束，因此可达性可直接用 BFS，复杂度 O(V + E)，无需排列、回溯或枚举简单路径。

自动保底先按实际弃牌规则计算候选集合。桌面和端点成本为 0，可抽牌成本为 1，弃牌和池外节点禁止访问；把节点进入成本转为边权，使用 0-1 BFS 找到需要新增牌最少的路线。所需新牌不超过可用手牌槽位才可构造保底。这解决“普通最短路跳数较短，但实际上需要补更多手牌”的误判。

有效路线只需一条作为构造证据。给手牌填入必需卡，再从合法余牌抽取干扰卡，最后打乱；起手也采用先路线后填充。随机性使用服务端持久保存的种子/随机状态与算法版本，不能每次重试重新取 Math.random，也不能因换算法改变旧局结果。

不在鼠标移动、倒计时刷新或纯重排时重做可达性判定；纯重排不改变可用节点集合。只在出牌补牌、换牌、刷新和弃牌等集合变化后检查。每个已接受命令最多一次自动保底，不递归。

2026-10-24 补充兜底：限定手牌出牌因所选位置无连接被拒绝、或没有换牌机会时，先检查整个可用牌集合；确实无解则直接执行一次原子保底，仍有路径则保持原手牌并提示改位置/换牌，不能通过错误猜测免费刷牌。重新读取旧的未锁定对局时也检查并在行锁内恢复，重复读取不多次刷新、不续期。自动刷新必须有清晰状态提示，不能只留下“未收录有效连接”的笼统报错。

单条路线校验是 O(L)，L 为路线长度；端点、重复人物、所有权和边存在性一次扫描完成。最佳成绩保存具体路线及首次达成时间，不为展示排行榜重复搜索最短路线。

### 4.4 请求与存储工作量

- 无游戏请求同步构建关系图、抓取网页或扫描全部任期。
- 节点显示信息按图版本一次加载，关系证据按边批量查询，避免一张牌/一条边一次 SQL 的 N+1 查询。
- 同一局每个已接受命令执行一次短 SQL 事务：版本检查、状态、幂等回执，以及必要的结束/结算任务。事务内没有网络抓取、图构建或大文件处理。
- 完整房间历史、完整关系图、原始 wiki 文本不进入活跃玩家状态 JSON。候选牌池按题目版本共享，玩家只存自己的剩余牌顺序/随机状态、手牌、桌面、弃牌和最佳结果。
- 状态量随本题牌池和实际卡牌数增长，不随每次操作反复复制历史。审计记录只存命令、判定和随机结果等增量，不每条都复制整局快照。
- 搜索优先使用按 graphVersion 缓存的公开昵称/别名小目录和本地索引，最多显示 20 条结果；不发完整关系图到浏览器。不能直接使用会随当前数据库变化的旧名单替代冻结的局内目录。
- 截止时间由服务端保存 deadline，客户端本地显示倒计时；不每秒向全部玩家广播剩余秒数。

## 5 代码组织与可靠性

### 5.1 模块边界

新增独立 `card-link` 业务域，并使用 `packages/card-link-core` 放共享类型、纯规则和不含 I/O 的图算法。只导出实际需要的接口，不建设可配置任意游戏的通用引擎。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| career 数据服务 | 身份、任期、来源、审核和修订 | 游戏回合、计时、Socket |
| graph 构建与读取 | 编译、校验、发布、版本加载和证据查询 | 更改玩家手牌 |
| 纯规则核心 | 命令验证、路径判定、发牌与状态转移 | SQL、Redis、HTTP、系统时钟 |
| 应用服务 | 身份检查、版本、事务、回执、状态恢复 | React 展示或直接拼页面文案 |
| HTTP/Socket 适配层 | 输入校验、调用应用服务、投递公共/私有结果 | 另一份规则判定 |
| 前端状态与组件 | 局面展示、输入草稿、待确认请求、动画 | 权威分数、发牌和队友关系裁决 |

纯核心显式接收时间和确定性随机输入，输出新状态与事件。无限/限定两策略复用路径和计分，不在各层散落 `if (mode === ...)`。练习/每日/好友/天梯作为场景策略设置权限、时限和结算，不复制状态机。

阶段统一使用 waiting/preparing/playing/roundOver/finished/cancelled 等明确状态，操作只在允许阶段进入；使用可穷尽的命令类型，避免多个互相矛盾的布尔标记。

### 5.2 与现有代码的复用边界

本轮已查看现有 `playerCache`、前端选手列表缓存、`services/keyLock` 以及图寻广播、共享回放和结果 outbox。

- 继续使用已有 Axios/Cookie/PoW、共享 Socket、Redis 前缀、角色及邮箱检查，不复制认证。
- 复用已有公开搜索匹配规则时，先将纯匹配函数提取到合适公共位置并保留旧调用行为；不能把新图谱目录硬塞进旧缓存导致其他游戏失效。
- 不让卡牌域调用 `location/store`、`roomView`、`recordResult` 或地图形状识别式 codec。复用其思想，不把图寻作为新游戏的底层框架。
- 不复制逐字段 `JSON.stringify` 比较整个房间的差分方式。规则输出本次变化字段，直接构造有类型的 patch。
- 不把分布式锁当成提交正确性的唯一保障。现有 keyLock 在 handler 完成后才可能报告租约丢失，因此数据库版本 CAS、唯一键和回执仍必须保护实际提交。
- 只在确有第二个调用者且契约一致时提取公共工具；本次不顺带重构全部经典多人、图寻或整个数据库层。

### 5.3 一个持久事实来源

SQL 持久保存权威局面、操作回执、每日进度和结算任务。Redis 保留匹配队列、Socket 适配、通知、可重建的到期索引及读取缓存。新卡牌域 Redis 丢失时能从 SQL 恢复；这不改变旧游戏 Redis 活跃数据仍不可随意清空的边界。

命令携带 `requestId`、本人的局面 revision 和回合阶段版本。幂等键按局/身份/请求唯一，同键不同内容返回冲突；重试原请求返回原回执。SQL 提交成功但响应丢失时，恢复以已提交结果为准。

不同玩家有独立局面 revision，不因对手出牌使本人所有输入冲突。回合关闭与命令提交必须在数据库层协调：PG 使用相应行锁/条件更新，SQLite 使用短事务与条件更新，确保截止后不能出现漏进结算的已确认动作。固定锁顺序，事务冲突只重试同一请求，不重抽。

匹配成功后，房间创建持久化并保证身份不同时进入多个活跃天梯局；断线继续原局。生产依赖不可用时不能静默回退成单进程内存房间。

### 5.4 状态同步与页面

公共视图与本人私有视图是显式白名单投影。出牌回执包含本人的 patch；其他人只在是否连通/锁定变化时收到公共 patch。协议包含 baseRevision 和 revision，缺口、乱序或重连时拉取相应全量视图。

投递通过共享 Socket/Adapter，不能仅对本进程连接有效。构造 patch 时就排除私人字段，禁止先广播完整房间再让前端隐藏。

前端以一个权威状态 reducer 管理服务端状态，拖拽草稿与待确认命令单独保存，不维护手牌、桌面、牌数的多份权威副本。拖动过程本地预览，落下才提交；结果未知时保留原 requestId。自动刷新不乐观生成卡牌。

入口为“娱乐 → 卡牌连接 → 选择玩法 → 选择场景”。页面懒加载；卡牌使用稳定人物/卡牌 ID。头像懒加载和固定尺寸，无图用占位，避免图标、动画和图片阻塞开局。移动端提供点选插入、移动、撤牌按钮，不仅支持拖拽。中英日文案沿用项目体系。

按用户后续要求，第一版卡片采用扑克牌形式，展示 ID、年龄和国籍。发牌、出牌与收牌使用短动画，受主菜单个人设置中的动画开关控制。长链横向滚动，移动端保留点选控制；首版不引入额外状态管理框架。

### 5.5 持久结果、历史和积分

- 每场保存一份共享结果，参与者结果以关联行引用；每局固定 graphVersion、rulesVersion、题目版本和牌池版本。
- 已发布图和来源版本不可变，回放使用显式版本 codec，不从当前选手库重新推断旧连接，也不直接套用图寻 codec。
- 图、题目与共享结果通过稳定引用去重；有活跃局、每日题或历史引用时不能删除。缓存 LRU 不等于持久清理政策。
- 完成局面和 SQL outbox 同事务提交；worker 重试完成结果及排名/积分。结果唯一键和 Elo 账本唯一键防止重复结算。
- Elo 更新使用该玩法的最新持久积分，按固定用户顺序锁定两方，在同一事务写双方积分及变更账本；失败整体回滚。待结算期间不让同一玩家进入下一场该玩法天梯，避免重试次序改变 Elo。
- 账号隐私、封禁、排行隐藏和访客登录后的成绩认领沿用现有规则；不直接重命名正在进行的访客局身份。

## 6 接口、数据库及运维契约

| 接口域 | 能力 |
| --- | --- |
| `/api/card-link` | 配置、冻结目录、创建/恢复单人局、提交命令、历史和榜单 |
| `card-link:*` Socket | 好友房、匹配、准备、命令、状态恢复和结算通知 |
| 外部任期接口 | 导出基准、提交带预期修订的变更，复用 Bearer scopes 和幂等机制 |
| 管理接口 | 任期审核、身份维护、受影响关系预览、构建/发布/停止新局使用某图版本 |

HTTP 和 Socket 调用同一应用服务及输入校验。共享类型区分玩法 `unlimited/limited`、场景 `practice/daily/friend/ranked`、人物 ID、旧 playerId、卡牌实例 ID、graphVersion 和局面 revision，不能用一个模糊的 version/ID 混用。

数据库对任期按人物、分队及起始日期建立查询索引；对边按图版本和人物对唯一；对操作回执按局、身份、请求唯一；对结算按 matchId 和玩法唯一；排行榜按玩法及积分索引。后台分页，证据/原始正文按需读取。具体 SQL 兼容 SQLite 和 PostgreSQL，不依赖 SQLite 宽松类型行为。

保留旧 JSON 和已发布历史，不建立维护成本不明的“旧字符串字段与新任期互相自动覆盖”。旧玩法继续按旧契约维护，任期更新只改变新关系资源；需要联动更正旧字段时生成独立可审阅差异。

新增表同时登记 schema、readiness、维护/备份清单和迁移测试。生产迁移由单独步骤运行，应用实例只做 readiness，不在两个实例启动时并发 DDL。

按数据准备、练习、每日、好友、天梯提供服务端开关，用于内部验收和故障降级；最终交付仍要求全部模式。停用新开局不丢弃进行中局及历史。回退优先切回已验证的图版本或关闭新入口，不删除新表、旧数据或重算成绩。

## 7 实施阶段与验收

### 7.1 阶段交付

| 阶段 | 交付与门槛 |
| --- | --- |
| 1 数据基础 | 身份、任期、来源、爬虫和审核；全量覆盖报告，每条异常可追踪 |
| 2 图与纯核心 | 可重复构建、原子发布、路径/发牌/保底算法；题目和起手有解检查 |
| 3 单人闭环 | 两玩法、每日、恢复、历史；验证状态事务与资源守恒 |
| 4 多人和天梯 | 好友房、独立竞速、双队列双积分、跨实例恢复与幂等结算 |
| 5 联合验收 | 性能、移动端、数据库兼容、故障演练、保真核验和发布准备 |

先用一条完整小数据链贯通抓取到回放，再扩大到全量资料；不能先做完整卡牌 UI，最后才发现任期或发牌语义不支持它。

### 7.2 正确性与回归

- 同队不同年代不连接，重复回归正确连接；同日转会、模糊日期、Present 冲突、租借、下放及员工角色覆盖。
- 不误合并主队/学院/国家分队，重复人物不能自连接；旧 team_history、导入和爬虫字段白名单兼容。
- 随机图和固定种子的性质测试：每副起手有解；保底成功后确实可解；卡牌分区不重叠且总数守恒；弃牌不复活；纯重排不奖励；机会始终为 0 或 1。
- 重点覆盖“最少跳数与最少新增卡不同”“刷新前有潜在路线但弃掉旧手牌后失效”“全图有路径但当前 7 槽无法恢复”等案例。
- 最佳路线不被更差结果覆盖；时间由服务端判定；更短优先；锁定和截止竞态、完全并列及退赛覆盖。
- 重复请求、请求同键异内容、响应丢失、跨实例同身份提交和不同玩家同时提交均不重复抽牌或计分。
- 双进程间操作、实例退出、Redis 通知丢失/重连、SQL 提交后崩溃及 outbox 重试；不能泄露对手私有内容。
- 图更新、人物改名、规则调参和缓存淘汰不改变旧局/每日/回放；缺失持久版本报明确错误，不能用最新版冒充。
- SQLite/PostgreSQL 迁移、原数据保留、旧接口契约和前端中英日/移动端回归。

### 7.3 性能目标与测量方法

所有指标在隔离数据、隔离 Redis 前缀和记录硬件/构建版本的环境测量。热缓存与冷启动分开报告，不能把人工体验替代延迟分布。

| 检查 | 初始验收目标 |
| --- | --- |
| 热态出牌、换牌、保底 | 基准为 100 个双人房，每位玩家平均每秒 1 个命令；服务端响应 p95 ≤ 150 ms、p99 ≤ 300 ms，不含公网往返 |
| 暖图开局 | p95 ≤ 300 ms；冷图加载单独记录，不把构建图耗时混入开局 |
| 图算法 | 用约 700 节点及 5,000 节点、稀疏/密集/断连合成图检查；无排列枚举或无界随机重试 |
| 存储与查询 | 热命令不读全量任期、不做证据 N+1；结果不按玩家复制整图，操作记录不复制全历史 |
| 同步 | 私人操作不广播对手手牌；无每秒全房间倒计时包；记录每命令及每房每秒字节量 |
| 内存与前端 | 连续 30 分钟混合开局/结束与图版本加载后缓存大小有界；桌面移动过程不发网络命令，目标设备上交互流畅 |

上述并发是容量验收基线，不是已证明的生产容量。SQLite 与 PostgreSQL 分别报告结果；若 SQLite 写入成为瓶颈，先检查事务长度、重复写和索引，生产容量以 PostgreSQL 实测为准，不能用减少持久确认来换取表面低延迟。

记录图构建耗时/节点边数、图缓存命中、命令延迟、保底耗时与触发原因、版本冲突、SQL 写耗时、广播字节及 outbox 重试。正常玩家主动弃牌导致的无解属于游戏事件；系统异常单独告警。日志不含 Token、Cookie 或玩家隐私牌堆全文。

### 7.4 数据保真与文档

测试使用 `scripts/test-integrated.ps1 -Suite server|client|scraper|all`，不继承真实环境进行破坏性测试。多人另外执行双进程演练；`pnpm test` 不代替爬虫验证。

实际迁移前重新采集基线、制作可恢复备份，在副本演练；保留选手 ID、旧历史、题库、图片、战绩和 Redis 活跃状态。完成后更新主接手手册及本文实施记录，记录真实测试、备份和未验证项，不能将待办写成已完成。
