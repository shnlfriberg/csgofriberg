# 图寻：真实素材采集与发布

首发目标是十图各 50 题（20 易、20 中、10 难），共 500 题。仓库包含十图的真实雷达资源；**尚无经过实测校准和人工审核的正式截图题目**。测试中的合成图片、测试题目和空白采集表均不属于正式素材。

日常出题只需截图、地图、楼层、雷达答案点位和难度，即可审核发布。游戏按雷达答案计分，实测 XYZ、视角、构建版本及校准均不作为发布条件。下文的实测坐标采集和校准流程用于需要 CS2 指令辅助定位的情况，可按需使用。

## 1. 固定采集环境

使用同一 CS2 构建，以及一致的画质和游戏 FOV。支持 1920×1080（1080P、16:9）、1280×960（960P、4:3）等原始截图；上传后先应用图片方向，再直接裁取正中心 360×360 像素，保存 WebP 与 240×240 缩略图，不保留大尺寸原图。宽高均需至少 360 像素。请让场景主体位于画面中心，四周内容会被裁掉。记录 Steam build ID 和游戏 `version` 输出。雷达与截图必须来自同一地图版本。升级游戏后重新提取雷达，完成校准并给题目建立新版本。

在本地练习地图运行 [location-capture.cfg](location-capture.cfg) 中的设置。移除机器人、HUD、雷达、武器模型和控制台画面。需要恢复正常游戏时重新加载常规配置。只拍摄可正常站立和到达的位置；不要以自由飞行摄像机或 noclip 位置作为答案。

如果需要坐标辅助，可在拍摄点执行 `getpos_exact`，记录控制台返回的 `setpos` 和 `setang` 信息。保持站立状态，确认记录对应玩家脚下位置而非眼睛高度；通过已知地面高度校验 Z。关闭控制台后保存原始 PNG。不使用坐标辅助时，直接在雷达图标出答案即可。

同一站立点不同朝向必须使用同一个 `capturePointId`。同一编号的 X/Y/Z 应一致；跨楼层即使 X/Y 相同，也应使用不同站立点编号。多层地图必须明确填写 `floorId`。

网站支持一个点位对应多张独立图片题，各自设置难度、视角和发布状态，共用位置答案。采集工作台可多次向同一点追加图片，图片名 `点位编号__后缀.png` 自动匹配；选择缩略图后逐图完善。第一张实测题目确定共用坐标，后续题目自动继承，新的原始指令须对应同一站位。完成一张不会移除点位或其它图片；已生成题目还可以通过“同点位新增图片题”继续加图。同一局和每日题单按点位去重，难度数量需同时考虑独立站位，不能仅按图片数量计算。

## 2. 雷达校准

已提取 Dust2、Mirage、Inferno、Nuke、Ancient、Anubis、Cache、Overpass、Vertigo、Train。当前资源中 Nuke、Vertigo 和 Train 各有上下两层，共 13 张雷达。游戏资源更新后以重新提取结果为准。

使用 [extract-location-radars.mjs](../scripts/extract-location-radars.mjs) 和 [Source 2 Viewer / ValveResourceFormat](https://github.com/ValveResourceFormat/ValveResourceFormat) 从本机 CS2 资源提取。示例：

```powershell
node scripts/extract-location-radars.mjs --vpk "E:/SteamLibrary/steamapps/common/Counter-Strike Global Offensive/game/csgo/pak01_dir.vpk" --vrf "/path/to/Source2Viewer-CLI.exe"
```

世界坐标转换使用原始雷达尺寸，不能使用网页显示尺寸：

```text
u = (worldX - posX) / (scale × width)
v = (posY - worldY) / (scale × height)
```

在“管理 → 图寻管理 → 地图管理”中，每层录入至少三个实测、分散、不共线的标定点。系统根据全部实测坐标与雷达标点，用最小二乘法自动计算原点 X/Y 和统一比例，预设或手填的旧参数不参与计算。网页会预览计算结果，服务端保存时独立重算，添加和删除点都会重新计算。多个楼层使用相同原点、比例和原始画布；只切换雷达图，不改变坐标系统。

校准检查针对计算后的偏差：每层存在任意三个点的归一化三角形面积因子超过 0.01，且每个点的归一化位置偏差不超过 0.005，即 0.5%。不再要求恰好前三点满足分布条件。页面显示逐点偏差、原图像素偏差及各层的基准点数量。点不足或分布退化时仍可发布手动标点题；出现较大拟合偏差时应复核坐标辅助的各点对应关系。检查地图可游玩区域外接矩形 `bounds`，尤其是有裁边配置的地图，它决定计分尺度。

校准区的“CS2 原始坐标指令”可以直接粘贴 `setpos_exact X Y Z;setang_exact PITCH YAW ROLL`，自动提取 X/Y，无需手工拆分；仅有 `setpos X Y Z` 也可用于校准。在雷达上独立点击人物实际站立位置后添加校准点，最后点击“保存”。“自动计算的原点与比例（只读）”展示实测结果，不需要管理员换算。已有校准点可以直接打开地图管理并保存，按新机制重新计算；旧地图版本快照保持原样。题目编辑窗口使用相同的原始指令输入方式，自动填写 XYZ、视角并按当前地图定位；FOV 按实际游戏设置填写。指令只用于提取数字，不会执行。无效或不完整的新指令不会沿用上一组坐标。

保存几何或校准配置会创建新的地图版本；旧题目必须重新核验并保存到新地图版本后才可用于新局。开放开关和排序不更改几何版本。已固定的每日题单与已开局对局继续使用原快照。

## 3. 采集清单和导入

生成空白的 500 行任务表：

```powershell
node scripts/location-capture-template.mjs .local-data/location-capture/capture.csv
```

将真实截图放在表格所在目录内的 `images/`。表格已填写地图、等级和建议文件名；采集人员必须补齐站立点编号、楼层、坐标、视角、时间、构建和来源。多层地图的楼层留空，避免误用默认层。FOV 的模板默认值也必须与实际游戏设置核对。

管理后台的地图配置 JSON 或 overview 响应可以保存为 `maps.json`，交给校验工具使用；不指定 `--maps` 时使用仓库初始概览，不能代替已完成的现场校准。

```powershell
node scripts/prepare-location-import.mjs --input .local-data/location-capture/capture.csv --maps maps.json --check
node scripts/prepare-location-import.mjs --input .local-data/location-capture/capture.csv --maps maps.json --out .local-data/location-import
```

工具检查：编号、明确楼层、测量数值、画布越界、裁剪后重复图片、同一拍摄点坐标一致性、原图宽高至少 360 像素、构建与来源。它复用网站的中心裁剪处理来检查图片，但导入目录仍保留原始截图，最终上传时统一处理。`--check` 仅验证；通过后生成包含 `manifest.json` 和图片的导入目录。也支持 JSON `questions[]` 输入，使用 `world` 和 `view` 对象。

在“题库备份与迁移 → 批量导入 JSON 清单”选择整个输出目录。前端上传图片后批量创建草稿，失败条目分别显示错误。日常录入优先使用“采集工作台”先标点后配图；单题也可在题目管理中上传和标注。图片转换为 WebP 和缩略图，移除元数据，公开 URL 使用随机 UUID；采集清单及原始命名只用于管理。

## 4. 人工审核清单

- 核对地图版本、楼层、截图与雷达答案点位；使用坐标辅助时另核对可选测量信息。
- 截图清晰，HUD、雷达、控制台、聊天和提示性元数据均已移除。
- 易题包含鲜明地标；中题需要组合线索；难题仍可定位，不收录纯墙面、天空和无识别线索的画面。
- 每图覆盖爆点、出生区、中路、连接通道和特色区域；检查重复站立点与区域集中度。
- 将草稿送审，再由审核人员发布。发布校验图片素材和有效雷达答案，不要求校准、世界坐标或拍摄视角。
- 查看“题库检查”，确认十图各等级达到 20/20/10，再检查每日三个互不重复题单和排除每日拍摄点后的随机题库配比。

已发布题目编辑后产生新版本；历史图片、答案、地图与评分保留在对局快照中，不重算旧战绩。不要覆盖或删除仍被历史回放引用的资源。

## 5. 题目点位合并（2026-10-29）

入口：管理后台 → 图寻管理 → 题目管理，选择地图和具体楼层后打开“题目合并”。该面板读取本楼层全部已入库题目与采集草稿的点位，不受题目列表的状态、难度、搜索和分页限制；尚未采纳的玩家投稿不属于正式题库，不在此面板中。

1. 点击雷达编号或勾选列表，选择两个或多个实际属于同一物体/墙面的相近点，每次最多 100 点。选中后显示其图片缩略图、题目数和待制作截图数。
2. 点击“选择合并位置”，雷达只保留选中点作为参考，再点击新的统一答案位置；也支持键盘方向键微调。
3. 核对数量和新位置，点击“确认合并到此处”。保留首个选中点的 `capturePointId`，所有关联题目统一地图、楼层及 u/v，每道题增加一个版本。图片 URL/哈希、题目 ID、来源、难度、发布状态、贡献统计保持不变。

已保存的采集草稿合并到一份，兼容旧 `asset` 和新 `images`，保留每张图片 ID 和素材。合并后待制作截图不能超过 100 张，超过时明确拒绝，需先完成部分题目制作；不截断或自动删除图片。旧实测 XYZ 不再适用新雷达标点，因此从当前题目/草稿移除，在旧题目版本及合并前记录中保留。未保存的浏览器本地采集点不在服务端合并范围。

服务端复用管理员 Cookie/PoW 链和 `location:catalog` 跨实例锁。`GET /api/admin/location/points?mapId=...&floorId=...` 返回轻量点位摘要、图片样例、当前内容指纹；`POST /api/admin/location/points/merge` 验证 2–100 个唯一点位、指纹、当前地图版本、同楼层及合法归一化坐标。指纹覆盖全部题目与草稿，即便另一管理员只新增同点图片也会阻止旧预览覆盖。旧地图版本或跨楼层异常点需先复核，不直接合并。

所有写入在一个 SQL 事务内完成；任一步失败整批回滚。`operationId` 对应 `location_versions` 的 `point-merge:<UUID>` 回执，同请求重复提交只返回原结果，修改内容复用 UUID 被拒绝。回执保存合并前完整题目/草稿，原题目版本、点位版本保留；无新增 SQL 表列，不提供自动撤销 UI。旧来源 `location_points` 模型保留其版本序列，活动点位由当前题目和草稿引用决定，因此不会作为重复候选显示。历史回放、已开局快照、已经固定的每日题单不回写，之后生成的新题单按合并后的点位去重。

测试与浏览器核验记录见主手册本次变更记录；验证日志及截图位于 `.local-data/verification/point-merge-*`。
