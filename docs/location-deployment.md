## 共享素材

`LOCATION_ASSET_DIR` 设置服务端上传资源的持久目录。Compose 的 app-1 和 app-2 同时挂载命名卷 `location-assets:/app/location-assets`；镜像内该目录拥有者为 distroless 的 nonroot（UID/GID 65532），新卷使用 Docker copy-up 初始化权限。根文件系统保持只读，上传写入共享卷。更换为已有卷或 bind mount 时，运维须预先核对 UID/GID 和两实例读写权限；不得临时改为 root 运行。

生产是 PostgreSQL，Redis 必须可用。Redis 保存活跃随机局、房间、匹配、断线期限和结果重试队列，应启用既有持久化配置。雷达初始资源随前端构建发布，后续管理员上传雷达使用同一个持久卷。上传资源是不可变 UUID 文件，缓存一年；不要覆盖旧 URL。

`Dockerfile` 保留 sharp 所需的平台可选依赖。`.dockerignore` 排除本地工具、测试夹具、开发数据和现有上传目录，避免把采集原图和测试运行时打入镜像。

## 发布

在隔离测试环境按项目原有流程运行 `pnpm install --frozen-lockfile`、`pnpm migrate`、`pnpm test` 和 `pnpm build`，Node 26 以上。生产镜像构建和 PostgreSQL 迁移沿用原 Compose migrate 服务；图寻新增表由现有统一迁移建立。迁移是新增表，不改原模式模型。

先备份，记录旧镜像摘要和当前配置，构建新镜像，再按仓库原部署流程更新 app-1 / app-2。测试上传一张隔离样图，经另一个实例读取同一 UUID URL；重启两实例后仍可读。检查健康端点和后台题库检查，再用真实已审核样题分别完成随机、每日和多人五轮。不要以首页可以打开代替部署验收。

本机演练支持：`pnpm --filter server exec vitest run test/location/socket.integration.test.ts --no-file-parallelism`。这项测试启动两个实际 Node 服务进程，20 间八人房，第一轮后停止一个进程，让 80 席位在另一个实例重连，五轮后核对 160 条唯一成绩；另测随机匹配、超时和退赛。测试使用独立配置的保留测试 IP，不更改生产代理信任规则。建议指定隔离的 DB_URL、REDIS_PREFIX 和 Redis 服务，禁止在生产数据库执行测试。

## 备份

在维护窗口阻止新局和上传，等待既有比赛完成和结果队列清空，停止应用写入。按仓库既有方案生成 PostgreSQL 一致性备份，同时归档 `location-assets` 卷；记录镜像、雷达构建、校准和评分版本，校验备份哈希与样图可读性。若需保留活跃房间，也应包含 Redis 持久化快照；仅备份数据库不能恢复未完成随机局和比赛。

恢复演练应使用独立环境：恢复数据库和资源卷，恢复权限，启动 Redis 及应用，随机检查历史回放和文件哈希。备份保留周期内不得清理旧资源。上线前必须完成生产存储实际备份与恢复演练。

## 回滚

停止新版本写入后使用记录的旧镜像启动，保留图寻表和共享素材卷。原模式不依赖新增表；软件回滚不需要删表或删图。已完成成绩不得重算。若因数据修复需要恢复备份，必须将数据库、资源卷和必要的 Redis 快照作为一组恢复，并核对备份之后新增成绩的处理方案。`docker compose down -v` 会删除持久卷，不用于常规发布或回滚。

开发分支已连接真实上游 `origin/main`（fe71776）；最初导入的源码快照保留在 `codex/imported-baseline` 以供恢复。功能改动仍在本地工作区，尚未推送或部署生产。
