## 3. 已复现的代码问题

下列复现只使用 `repro.sqlite3` 和独立 Redis DB15 前缀；只关闭复现进程自身的 Redis 客户端，没有停止真实 Redis 或故障注入运行中的本机 API。

### P1：Redis 必须可用的配置未被图寻状态存储遵守

位置：`server/src/location/store.ts:18–47`、`:104–120`，以及共用 `services/keyLock.ts` 的无 Redis 分支。

`redis()` 不可用时，图寻无条件读取/写入进程内 fallback，未判断 `config.redisRequired`。本次设置 `REDIS_REQUIRED=true`，断开隔离进程的 Redis 连接后调用 `startGame` 仍成功；恢复连接后，同一个 gameId 通过 `loadGame` 返回 null。原模式 `roomStore` 对同类情况有显式拒绝保护，图寻没有。

影响：运行中 Redis 故障期间，玩家可能获得一个只存在于某个进程的新局；恢复或换实例后消失。目录编辑共用锁在不可用期间也会退回本机互斥，不能提供生产跨实例互斥。本次具体复现的是单人状态丢失，未对真实目录制造竞争写入。

建议：生产强制 Redis 时，所有相关状态/锁入口明确返回 503；本机显式单实例环境才允许 fallback。增加“连接丢失→拒绝写入→恢复后原状态可读”及跨实例验证。

### P1：单人最后一题的 SQL 成绩与 Redis 终局状态缺少一致恢复

位置：`server/src/location/games.ts:289–299`；`:254–255` 的冲突忽略。

顺序为先 `recordResult` 写 SQL，再 `saveGame` 写 Redis。复现让 SQL 成功后的一次 Redis MULTI/EXEC 失败：永久成绩已为 25,000，Redis 仍显示 playing / 已答四题。随后以新请求 ID 更换第五题答案重试，接口返回 finished / 20,000，但 `replay` 仍是 25,000，因为已有成绩被 onConflict.ignore 保留。

影响：异常恢复后玩家看到的终局、历史回放和统计可能不一致。默认前端会保留原请求重试，可减小常规触发概率，但服务端允许改答路径仍存在；不能依靠前端来保证永久结算一致。

建议：使持久化终局/回执成为重试依据，或用可恢复持久任务保证最终状态一致；已经有正式结果时返回该结果，不再接受新的终局答案。补 SQL 成功/Redis 失败、失去回执、不同请求 ID 重试的回归。

### P2：图寻每日榜未排除封禁用户

位置：`server/src/location/routes.ts:213–226`。

榜单查询只检查 `leaderboard_hidden=false`，没有 `whereNull('u.banned_at')`。隔离库创建已封禁测试账号及旧日期每日成绩后，真实路由返回 200，账号仍排第 1。图寻贡献榜已有封禁过滤，两个榜行为不一致。

建议：补充封禁过滤，并测试封禁前后、隐藏排行及恢复后的行为；不删除旧成绩。

### P2：多人公共视图暴露内部访客身份 key

位置：`server/src/location/roomView.ts:14`、`:26–27`、`:47`，并通过 room broadcast 和多人回放传播。

`players[].key`、`results[].key`、`host` 直接采用 `identity.key`。用两名不同访客的房间验证，A 的视图包含 B 的原始 `g:<guestKey>`。应改用公开展示标识或房间范围的不可认证标识，并兼容本人、排名和旧回放映射。

当前登录/访客认证仍验证签名 Cookie，因此本项证明的是内部身份标识暴露，**没有证明只凭 guestKey 就能接管账号**。不应把此项夸大成已验证的越权登录。
